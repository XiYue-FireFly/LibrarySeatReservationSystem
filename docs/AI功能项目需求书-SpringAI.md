# 图书馆座位预约系统 AI 功能项目需求书

## 1. 项目背景

现有系统是一个基于 Spring Boot 3 + Spring Cloud Gateway + OpenFeign + MyBatis-Plus 的实验室/图书馆座位预约系统，已包含学生端、管理员端、用户服务、预约服务、网关服务和公共模块。系统当前支持学生登录注册、实验室查询、座位查询、预约、取消预约、反馈、通知，以及管理员实验室和座位运维。

为提升用户体验，计划新增基于 Spring AI 的智能助手能力。AI 助手通过自然语言理解用户意图，结合 RAG、工具调用和用户长期记忆，帮助用户完成预约、取消、查询、聊天咨询和个性化推荐等操作。

## 2. 建设目标

### 2.1 总体目标

建设一个可接入多家大模型供应商的智能预约助手，使用户可以用自然语言完成系统内主要操作，并获得基于个人习惯和实时座位数据的推荐。

### 2.2 具体目标

1. 支持用户在前端以聊天方式与 AI 交互。
2. 支持用户或管理员在页面中接入 OpenAI、Azure OpenAI、Ollama、通义千问、智谱、DeepSeek 等模型供应商。
3. 支持 RAG 检索系统文档、预约规则、实验室说明、管理员公告和常见问题。
4. 支持 AI 调用后端业务工具完成实验室查询、座位查询、预约、取消预约、查询预约记录、查询通知、提交反馈等操作。
5. 支持记忆用户偏好，例如常用实验室、常用时段、偏好座位位置、学习时长、取消习惯等。
6. 支持根据实时数据和用户习惯推荐座位、时间段和实验室。
7. 支持敏感操作确认，避免 AI 直接误预约或误取消。
8. 支持管理员管理 AI 知识库、提示词、模型配置和审计记录。

## 3. 用户角色

### 3.1 学生用户

学生可以通过 AI 助手完成：

1. 咨询预约规则。
2. 查询实验室开放状态和空闲座位。
3. 让 AI 推荐合适座位。
4. 通过确认流程完成预约。
5. 查询自己的预约、通知和反馈。
6. 取消预约。
7. 提交座位问题反馈。
8. 让 AI 记住个人偏好。

### 3.2 管理员用户

管理员可以通过 AI 助手完成：

1. 查询实验室运行状态。
2. 查询高峰时段、热门实验室和异常预约情况。
3. 查询学生反馈摘要。
4. 管理知识库资料。
5. 配置 AI 模型供应商。
6. 查看 AI 操作审计日志。

### 3.3 超级管理员

超级管理员可以完成：

1. 管理全局模型配置。
2. 管理工具调用权限。
3. 管理敏感操作策略。
4. 查看全系统 AI 使用统计和风险日志。

## 4. 功能需求

### 4.1 AI 聊天助手

用户可以在学生端和管理员端发起聊天。AI 需要根据用户身份、上下文、系统规则和业务数据回答问题。

典型问题：

1. “明天下午 2 点帮我找一个安静的座位。”
2. “我今天有哪些预约？”
3. “帮我取消今天晚上 7 点的预约。”
4. “我喜欢靠窗的位置，之后优先推荐。”
5. “计算机实验室 1 现在还有空位吗？”
6. “预约规则是什么？”

验收标准：

1. AI 能区分闲聊、规则咨询、查询、推荐、预约、取消等意图。
2. AI 回答必须结合当前用户身份。
3. AI 对预约和取消等写操作必须先生成确认信息，用户确认后才能执行。
4. AI 不能泄露其他用户的真实姓名、账号、手机号、邮箱等隐私信息。

### 4.2 多模型接入与页面配置

系统需要支持多模型供应商配置。API Key、请求协议、Base URL、模型名称等信息不在底层代码中写死，而是由用户或管理员在页面中录入。

模型类型：

1. 云端模型：OpenAI、Azure OpenAI、通义千问、智谱、DeepSeek。
2. 本地模型：Ollama。
3. 嵌入模型：OpenAI Embedding、Ollama Embedding、BGE 类本地向量模型。

配置能力：

1. 每个模型供应商可配置协议类型、Base URL、API Key、模型名称、temperature、timeout。
2. 协议类型至少支持 OpenAI-compatible、Ollama、Azure OpenAI、自定义 HTTP 协议。
3. 用户可配置自己的私有模型连接，用于个人 AI 助手。
4. 管理员可配置系统默认模型连接，用于无私有配置的用户。
5. 支持按用户、角色或业务场景选择模型，例如聊天模型、推荐模型、摘要模型、嵌入模型分离。
6. API Key 不写入代码仓库，也不要求部署时预先写死在后端配置中。
7. API Key 入库前必须加密，页面再次展示时只能显示脱敏值。
8. 支持“测试连接”功能，用于验证 Base URL、Key 和模型名称是否可用。

验收标准：

1. 用户可在页面新增、修改、删除自己的模型配置。
2. 管理员可在页面新增、修改、删除系统模型配置。
3. 修改页面配置即可切换模型供应商。
4. 单个模型不可用时，系统能返回友好错误。
5. 不同模型调用日志可被追踪。
6. 后端日志不能打印完整 API Key。

模型配置页面字段建议：

1. 配置名称：例如“我的 DeepSeek”“本地 Ollama”。
2. 供应商类型：OpenAI-compatible、Ollama、Azure OpenAI、Custom。
3. 请求协议：HTTPS、HTTP，或自定义协议标识。
4. Base URL：例如 `https://api.openai.com`、`http://localhost:11434`。
5. API Key：密码输入框，保存后脱敏展示。
6. Chat Model：聊天模型名称。
7. Embedding Model：向量模型名称。
8. Temperature：生成随机性。
9. Timeout：请求超时时间。
10. 是否默认：设置为个人默认或系统默认。

### 4.3 RAG 知识库问答

系统需要把项目文档和业务知识导入向量库，用于增强问答。

知识来源：

1. `README.md`、`API.md`、项目接口文档。
2. 实验室规则、预约规则、签到规则、取消规则、处罚规则。
3. 管理员公告、实验室说明、座位使用说明。
4. 常见问题 FAQ。
5. 管理员上传的 Markdown、PDF、Word、纯文本资料。

知识库功能：

1. 文档上传。
2. 文档切分。
3. 向量化入库。
4. 检索召回。
5. 基于检索结果生成回答。
6. 文档版本管理。
7. 知识库命中来源展示。

验收标准：

1. 用户询问规则时，AI 优先根据知识库回答。
2. 回答能展示来源标题或文档片段编号。
3. 文档更新后可重新向量化。
4. 对未命中知识库的问题，AI 需要说明不确定，不能编造规则。

### 4.4 AI 工具调用

AI 需要通过 Spring AI Tool Calling 调用后端业务能力。

第一阶段工具：

1. `listLabs`：查询实验室列表。
2. `listSeats`：查询指定实验室和时间段的座位状态。
3. `getMyBookings`：查询当前用户预约。
4. `createBookingDraft`：生成预约草案，不直接落库。
5. `confirmBooking`：用户确认后创建预约。
6. `cancelBookingDraft`：生成取消预约草案。
7. `confirmCancelBooking`：用户确认后取消预约。
8. `getMyNotifications`：查询通知。
9. `submitFeedbackDraft`：生成反馈草案。
10. `confirmSubmitFeedback`：用户确认后提交反馈。

第二阶段工具：

1. `recommendSeat`：根据偏好和实时座位数据推荐座位。
2. `summarizeFeedback`：管理员查看反馈摘要。
3. `analyzePeakHours`：分析高峰时段。
4. `explainBookingFailure`：解释预约失败原因。

验收标准：

1. 读操作可直接执行。
2. 写操作必须二次确认。
3. 工具调用必须记录审计日志。
4. 工具层必须校验用户权限，不能只依赖模型判断。
5. 工具参数必须结构化，不能让模型拼接 SQL。

### 4.5 用户记忆与个性化推荐

系统需要记录用户偏好，并用于推荐。

记忆类型：

1. 显式偏好：用户直接说“我喜欢靠窗”“我一般下午学习”。
2. 行为偏好：从历史预约中统计常用实验室、常用时段、平均学习时长、取消率。
3. 负反馈偏好：用户说“不想去太吵的区域”“不要推荐维护频繁的座位”。
4. 临时上下文：当前会话中的时间、地点、任务目标。

推荐维度：

1. 实验室可用状态。
2. 座位空闲状态。
3. 用户常用时段。
4. 用户常用实验室。
5. 座位维护状态。
6. 预约冲突。
7. 用户处罚状态。

验收标准：

1. 用户可以新增、查看、删除自己的偏好记忆。
2. 推荐结果需要说明理由。
3. 用户可以关闭个性化推荐。
4. 记忆数据不得跨用户泄露。

### 4.6 对话上下文管理

系统需要支持多轮对话。

要求：

1. 每个用户可以拥有多个会话。
2. 每个会话有 `conversationId`。
3. 短期上下文保存最近 N 轮对话。
4. 长期记忆单独结构化存储。
5. 对话过长时自动摘要。

验收标准：

1. 用户连续表达“明天下午”“就刚才那个实验室”“帮我预约第二个推荐”时，AI 能理解上下文。
2. 刷新页面后，历史会话可恢复。
3. 敏感信息不进入长期记忆，除非用户明确授权。

### 4.7 前端功能

学生端新增：

1. AI 助手入口。
2. 聊天页面。
3. 推荐卡片。
4. 预约确认卡片。
5. 取消确认卡片。
6. 知识库来源展示。
7. 偏好管理页。

管理员端新增：

1. AI 助手入口。
2. 知识库管理。
3. 模型配置管理：录入供应商、协议链接、Base URL、API Key 和模型名称。
4. 工具调用审计。
5. AI 使用统计。

学生端新增：

1. 个人 AI 模型配置页。
2. API Key 录入和脱敏展示。
3. 连接测试按钮。
4. 默认模型选择。
5. 是否使用系统默认模型开关。

验收标准：

1. 移动端和桌面端均可使用。
2. 写操作确认卡片必须清晰展示实验室、座位、开始时间、结束时间和风险提示。
3. 聊天失败时有重试入口。

## 5. 非功能需求

### 5.1 安全

1. AI 服务必须通过网关鉴权。
2. 所有工具调用必须携带 `X-User-Id` 和 `X-User-Role`。
3. 写操作必须校验数据归属。
4. 模型提示词中不得包含明文 API Key。
5. 长期记忆需要用户可控。
6. 管理员工具不得开放给学生。

### 5.2 隐私

1. 默认不把用户真实姓名、账号、头像等隐私数据发送给第三方模型。
2. 必要时发送脱敏数据。
3. 对话日志可以开启脱敏存储。
4. 用户可以删除自己的 AI 记忆。

### 5.3 稳定性

1. 模型调用超时需要降级。
2. 工具调用失败需要给出可理解的原因。
3. AI 服务异常不能影响原预约功能。
4. 高并发预约仍以 reservation-service 的业务校验为准。

### 5.4 可观测性

1. 记录模型供应商、模型名称、耗时、token 用量、成功失败状态。
2. 记录工具调用名称、参数摘要、调用结果、操作者。
3. 支持管理员按用户、时间、工具类型查询日志。

## 6. 推荐新增微服务

建议新增 `ai-service` 微服务，而不是直接把 AI 能力塞进现有 `reservation-service`。

原因：

1. AI 依赖和普通业务依赖不同，独立服务更清晰。
2. 模型调用可能慢，独立服务便于限流、熔断和扩容。
3. RAG、向量库、记忆和审计属于独立领域。
4. 不影响现有预约核心链路稳定性。

服务边界：

1. `ai-service` 负责聊天、RAG、工具编排、记忆、推荐、审计。
2. `reservation-service` 继续负责预约、取消、座位、实验室等强一致业务。
3. `user-service` 继续负责用户、通知、头像、账号状态。
4. `library-gateway` 负责统一鉴权和转发。

## 7. 数据需求

建议新增数据表：

1. `ai_conversation`：AI 会话表。
2. `ai_message`：AI 消息表。
3. `ai_user_memory`：用户长期记忆表。
4. `ai_knowledge_document`：知识库文档表。
5. `ai_knowledge_chunk`：知识切片元数据表。
6. `ai_tool_audit_log`：工具调用审计表。
7. `ai_model_config`：模型配置表，保存用户或管理员在页面中录入的协议、Base URL、模型名称和加密后的 API Key。
8. `ai_recommendation_log`：推荐记录表。

向量库选择：

1. 本项目明确使用 PostgreSQL + pgvector 进行 RAG 向量处理。
2. MySQL 继续承载现有业务数据和 AI 管理数据，例如用户、预约、会话、消息、模型配置、记忆、审计日志。
3. PostgreSQL Vector 专门承载知识库向量数据，例如文档切片、embedding 向量和相似度检索索引。
4. Spring AI 侧使用 PGVector VectorStore 对接 PostgreSQL + pgvector。
5. 向量检索距离建议使用 COSINE_DISTANCE，索引建议使用 HNSW。

## 8. 业务流程

### 8.1 AI 推荐并预约

1. 用户输入：“明天下午帮我找一个座位。”
2. AI 解析时间范围。
3. AI 调用用户记忆，获得偏好实验室和时段。
4. AI 调用 `listLabs` 查询实验室。
5. AI 调用 `listSeats` 查询可用座位。
6. AI 生成推荐理由。
7. 用户选择推荐项。
8. AI 生成预约草案。
9. 用户点击确认。
10. 系统调用 `confirmBooking` 创建预约。
11. 返回预约结果并写入推荐日志。

### 8.2 AI 取消预约

1. 用户输入：“取消我今晚的预约。”
2. AI 调用 `getMyBookings` 查询预约。
3. 如果只有一条匹配预约，生成取消确认卡片。
4. 如果有多条匹配预约，让用户选择。
5. 用户确认后调用 `confirmCancelBooking`。
6. 返回取消结果。

### 8.3 AI 规则问答

1. 用户输入预约规则问题。
2. AI 使用 RAG 检索知识库。
3. 根据知识库和系统提示词回答。
4. 展示来源。
5. 无来源时说明无法确定。

## 9. 验收范围

### 9.1 MVP 验收

1. AI 聊天可用。
2. 可接入至少一个云端模型和一个本地 Ollama 模型。
3. 支持 RAG 查询预约规则。
4. 支持查询实验室、查询座位、查询我的预约。
5. 支持预约和取消的确认式工具调用。
6. 支持基础用户偏好记忆。
7. 支持聊天记录和工具调用审计。

### 9.2 完整版验收

1. 多模型配置后台。
2. 知识库上传和重建索引。
3. 个性化座位推荐。
4. 管理员 AI 分析助手。
5. AI 使用统计和成本统计。
6. 风险控制和脱敏策略完善。

## 10. 风险与约束

1. 大模型可能误解用户意图，因此写操作必须二次确认。
2. 模型供应商接口、价格和限额可能变化，因此要通过配置解耦。
3. RAG 结果依赖知识库质量，需要管理员维护文档。
4. 推荐不能绕过原有预约冲突校验。
5. 用户记忆属于隐私数据，需要可查看、可删除、可关闭。
